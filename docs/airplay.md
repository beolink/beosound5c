# AirPlay 2

BeoSound 5c can appear on the network as an AirPlay 2 speaker, so anything on
an iPhone, iPad or Mac can be sent to it — including as part of a multi-room
group alongside HomePods and other AirPlay 2 devices, and from the Home app.

## How it fits together

```
iPhone/Mac ──AirPlay 2──▶ shairport-sync ──▶ pipewire-pulse ──▶ beo_tone_sink ──▶ DAC ──▶ amp
                               │                                (tone filter chain)
                               ├── metadata pipe ──▶ beo-source-airplay ──▶ beo-router ──▶ UI
                               └── D-Bus ◀── source switch (DropSession), transport (DACP, see below)
```

Three moving parts:

| Component | Role |
| --- | --- |
| `nqptp` | PTP clock daemon. AirPlay 2 will not work without it. Runs as root (ports 319/320). |
| `beo-shairport` | shairport-sync itself: terminates the AirPlay session, writes audio into PipeWire, emits metadata. |
| `beo-source-airplay` | Reads the metadata pipe, registers the source with the router, serves cover art, proxies transport buttons. |

Audio deliberately goes through the same PulseAudio backend that
`go-librespot` uses, so it lands on `beo_tone_sink` and inherits tone control
and the normal PowerLink/MasterLink output path. Nothing extra to wire up.

AirPlay is the only **push** source on the device: playback starts because
someone picked the BeoSound on their phone, not because a menu item was
selected. The metadata pipe reader drives source registration, and
`handle_activate` refuses to claim "playing" when no sender is connected.

## Installing

`install/modules/airplay.sh` does all of it (`install_airplay`). It builds from
source because there is no usable package — see the traps below.

## Configuration

`/etc/beosound5c/shairport-sync.conf` is generated by the install module. In
`config.json`:

```json
"menu": { "AIRPLAY": "airplay" },
"airplay": { "source": "cd", "mode": "auto" }
```

* The `menu` entry makes the source appear. Without it the service exits at
  startup by design (`SourceBase.start` menu guard).
* `airplay.source` claims a Beo4 source button. `"cd"` routes the Beo4 **CD**
  key to AirPlay: Beo4 CD → ML `GOTO_SOURCE 0x8D` → `ML_SOURCE_TO_ACTION` →
  `router._source_buttons` → this source. Only claim a button no other source
  claims; the router logs the resulting map as
  `Device type handling: ... (sources: amem->spotify, cd->airplay, ...)`.

* `airplay.mode` picks which AirPlay service is advertised, resolved into
  `--service-type` by `services/system/beo-shairport-launch.sh`:

  | mode | multi-room + Home app | transport control from the BeoSound |
  | --- | --- | --- |
  | `airplay2` | yes | no |
  | `classic` (AirPlay 1) | no | yes |
  | `auto` (default) | AirPlay 2 when nqptp is running, else classic | |

  Switching is a config edit plus `systemctl restart beo-shairport`. Why the
  trade-off exists is explained under *Transport control* below.

Volume is deliberately owned by the BeoSound (`ignore_volume_control = "yes"`),
matching `external_volume: true` on go-librespot. Set it to `"no"` if the
sender's volume slider should attenuate the stream instead.

## Transport control, and why it usually does not work

The BeoSound's own transport keys are proxied back to the sender over DACP,
via shairport-sync's D-Bus `RemoteControl` interface. In practice this only
works for AirPlay 1 / "Realtime" streams.

An **AirPlay 2 buffered stream carries no DACP credentials**. Verified by
reading the metadata pipe through live sessions from both macOS and iOS — the
Music app on either picks `StreamType = "Buffered"`, and in both cases:

```
ssnc/daid: ABSENT     (DACP-ID)
ssnc/acre: ABSENT     (Active-Remote token)
ssnc/dapo: ABSENT     (DACP port)
```

So this is a property of the stream type, not of a particular sender.

The sender still advertises `_dacp._tcp` on the network, but without the
Active-Remote token there is no way to authenticate to it. shairport-sync
reports this as `RemoteControl.Available = false` while `StreamType` is
`"Buffered"`.

The trap: **the D-Bus method returns success anyway.** Calling `PlayPause` on
an unavailable remote reports "ok" and does nothing, so `_remote()` checks
`Available` first rather than trusting the call's result — otherwise every
dead button cheerfully reports that it was sent.

This has a consequence beyond dead buttons. When another source takes over,
the router forwards `stop`, and a sender that cannot be paused simply keeps
pushing audio into the same sink as the incoming source — both play over each
other. So when `Pause` is unavailable the source falls back to `DropSession`,
which ends the AirPlay session outright. That is the only reliable way to
silence AirPlay on a source switch.

One more consequence: `RemoteControl.PlayerState` stays correct even when
`Available` is false, so it — not the pipe — is the authority on playback
state. The pipe's `pbeg`/`pfls`/`prsm` are one-shot events and are missed
entirely if beo-source-airplay restarts mid-stream, which used to leave the
source sitting on "available" while audio was plainly playing. A slow
reconcile loop (`STATE_POLL_INTERVAL`) pulls state back in line.

If transport control matters more than multi-room, switch to classic AirPlay 1
with `airplay.mode` (below) — no rebuild needed, and nothing else in this
integration changes.

## Traps

Three things cost real time here; none of them fail loudly.

**1. `--with-pa` is not a configure flag.** It is silently ignored
(`configure: WARNING: unrecognized options: --with-pa`) and you get an
ALSA-only binary. The flag is `--with-pulseaudio`. Check the result:

```bash
shairport-sync -V   # must list PulseAudio, and AirPlay2
```

**2. Do not use `--with-pipewire` when PipeWire came from backports.** The
native backend needs `libpipewire-0.3-dev`, and if the distro's dev package is
older than the installed runtime, apt resolves the conflict by *downgrading*
the running PipeWire library. The PulseAudio backend reaches PipeWire through
`pipewire-pulse` anyway.

**3. The D-Bus policy does not cover the service user.** shairport-sync runs
as the service user so it can reach that user's PipeWire graph, but upstream's
policy grants ownership of `org.gnome.ShairportSync` only to `root` and to a
packaged `shairport-sync` user. Without an added policy it logs:

```
could not acquire a Shairport Sync native D-Bus interface
"org.gnome.ShairportSync" on the system bus
```

Audio and metadata still work; only transport control from the BeoSound's own
buttons goes dead. `install/modules/airplay.sh` writes the extra policy to
`/etc/dbus-1/system.d/beo-shairport-dbus.conf` — a separate file, so
reinstalling shairport-sync does not revert it.

Also worth knowing: Debian's packaged `shairport-sync` is AirPlay **1** only.
Its dependency list has no libplist, libsodium or ffmpeg, which is the quickest
way to tell without installing it. And `plistutil` (package `libplist-utils`)
is a build-time binary dependency of `--with-airplay-2` that `libplist-dev`
does not pull in.

## Checking it works

```bash
systemctl is-active nqptp beo-shairport beo-source-airplay
curl -s localhost:8775/status            # play_state, session, pipe_present
avahi-browse -rt _airplay._tcp           # the device should be listed on port 7000
busctl --system introspect org.gnome.ShairportSync /org/gnome/ShairportSync
```

`RemoteControl.Available` is `false` until a sender connects; that is normal.
